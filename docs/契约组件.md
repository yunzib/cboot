# 契约组件

契约组件是 cboot 中**按现有 Bean 契约编写、由应用显式选择**的一组 bean。
它不是运行期插件：没有 DLL/so 加载，没有运行期注册；组件、依赖和 bean 清单
都在编译期确定。

本文是使用手册，说明如何编写组件、声明依赖、在应用中选择组件，以及构建和排查。

---

## 1. 概念与边界

一个契约组件由两部分组成：

1. **一组普通 cboot bean**：注解、构造器注入、生命周期、路由、配置、Profile
   全部沿用现有规则。
2. **一个组件描述符**：声明组件名、贡献的 bean、直接依赖的组件。

组件内部的 bean 和应用 bean 没有区别。区别只在装配边界：

```cpp
// 全局命名空间：应用 bean，自动发现
struct [[=Bean{}]] AppService { ... };

// 组件 namespace：只有被应用 components 选中才装配
namespace cache {
struct [[=Bean{}]] MemoryCache { ... };
}
```

契约组件适用于：

- 第三方能力的接入包：Redis、数据库、消息队列、指标、鉴权
- 一组需要一起装配的 bean
- 需要声明组件间依赖、由框架在编译期补齐的场景

不适用于：

- 运行期安装、卸载、热更新
- 跨编译器/跨 ABI 的二进制插件
- 只包含类型/工具函数、不贡献 bean 的普通库（直接做基础包或普通模块）

## 2. 快速开始

### 2.1 编写组件

```cpp
// cboot.cache.cppm
export module cboot.cache;

import std;
import cboot.core.annotations;   // Bean / bean_name
import cboot.meta.reflect;        // type_list

export namespace cache {

struct [[=Bean{}]] MemoryCache {
    int value() const { return 42; }
};

} // namespace cache

export struct cache_component {
    static constexpr bean_name name{"cache"};
    using beans = type_list<cache::MemoryCache>;
    using dependencies = type_list<>;
};
```

### 2.2 应用选择组件

```cpp
import cboot.app;
import cboot.cache;

struct App : application<App> {
    using components = type_list<cache_component>;
};

int main() { return App{}.run(); }
```

`cache::MemoryCache` 会进入 bean 清单，参与构造器注入、生命周期、路由和健康检查。

## 3. 组件契约

### 3.1 描述符

组件描述符是普通结构体，不是 bean：

```cpp
export struct redis_component {
    static constexpr bean_name name{"redis"};   // 可选
    using beans = type_list<
        redis::Props,
        redis::Client,
        redis::HealthCheck>;
    using dependencies = type_list<>;           // 只写直接依赖
    using hooks = type_list<>;                  // 可选：非 bean 的挂载点
};
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 否 | 诊断用名字，类型为 `bean_name` |
| `beans` | 是 | `type_list<...>`，本组件贡献的 bean |
| `dependencies` | 否 | `type_list<组件...>`，直接依赖的组件 |
| `hooks` | 否 | `type_list<...>`，组件挂载点；见 3.4 |

注意：

- 字段名是 `dependencies`，不是 `requires`（后者是 C++ 关键字）。
- 描述符不加 `[[=Bean{}]]`，不参与自动发现。
- 描述符必须 `export`，应用 import 后才能引用。
- `beans` 里的类型必须是完整、非模板的类类型。
- `dependencies` 只写直接依赖；传递依赖由框架补齐。

### 3.2 组件 bean 规则

组件 bean 就是普通 bean：

- 必须带 `[[=Bean{}]]` / `[[=Bean{"name"}]]`，或 `[[=Config{"prefix"}]]`
- 控制器也是 bean；有路由方法必须带 `[[=Bean{}]]`
- 构造器注入 `T&`；多构造器使用 `[[=Inject{}]]`
- 同基类多实例使用 `[[=Bean{"name"}]]` + `[[=Named{"name"}]]`
- 生命周期使用 `[[=PostConstruct{}]]` / `[[=PreDestroy{}]]`
- 条件装配使用 `[[=Profile{"name"}]]`
- 事件、定时、路由注解按现有规则使用
- 跨模块类型必须由组件模块 `export`

### 3.3 命名空间

组件 bean 必须放在组件自己的命名空间，不能是全局命名空间的直接成员：

```cpp
namespace redis {
struct [[=Bean{}]] Client { ... };
}
```

原因：应用会自动扫描全局命名空间中的 `[[=Bean{}]]` / `[[=Config{}]]`。
如果组件 bean 直接放全局命名空间，应用即使不写 `components`，只要 import
组件模块就会被动装配，显式选择失效。

约定：

- 全局命名空间：应用自己的 bean
- 组件命名空间：组件 bean
- 描述符可以放全局命名空间（类型名唯一），也可以放组件命名空间

### 3.4 组件 hooks（高级）

`hooks` 用于贡献**非 bean** 的编译期挂载点，适合需要访问整个 bean 清单的
基础设施（如定时任务调度器）。

Hook 类型提供嵌套 RAII 实例：

```cpp
struct my_hook {
    template <class Ctx>
    struct instance {
        explicit instance(Ctx& ctx);   // 安装/启动
        ~instance();                   // 停止/清理
        instance(const instance&) = delete;
    };
};
```

```cpp
export struct my_component {
    using beans = type_list<>;
    using dependencies = type_list<>;
    using hooks = type_list<my_hook>;
};
```

生命周期：

- 在 `context` 全部 bean 构造完成后安装
- 在 `context` 析构前停止
- 多个 hook 按组件闭包顺序安装；同一 hook 类型去重
- Hook 可以读取 `Ctx::bean_count`、`Ctx::bean_type<I>`，通过
  `ctx.is_active<I>()` / `ctx.get_at<I>()` 访问 bean

不经过 `application`、只用 `context` 时，用 `hook_scope` 显式安装：

```cpp
context<A, B> ctx;
hook_scope<decltype(ctx), my_hook> hooks(ctx);
```

`hook_scope` 从 `cboot.core.context` 导出，`cboot.app` 也 re-export。

`cboot.schedule` 就是一个只贡献 hook 的组件：无 bean，安装后扫描
`[[=Scheduled{...}]]` 方法并启动调度线程。原理和自定义 hook 示例见
[定时任务](定时任务.md)。

## 4. 应用声明

### 4.1 选择组件

```cpp
import cboot.app;
import cboot.redis;

struct ShopApp : application<ShopApp> {
    using components = type_list<redis_component>;
};
```

### 4.2 多个组件

```cpp
import cboot.redis;
import cboot.metrics;
import cboot.jwt;

struct ShopApp : application<ShopApp> {
    using components =
        type_list<redis_component, metrics_component, jwt_component>;
};
```

### 4.3 不选择组件

没有 `components` 时退化为空清单：

```cpp
struct ShopApp : application<ShopApp> {
    // 无 components
};
```

### 4.4 显式 bean 清单

需要精确控制 bean 集合时，仍可使用逃生口：

```cpp
int main() {
    return run<UserApi, UserService, UserRepo>(8080);
}
```

显式清单不经过组件展开。

## 5. 依赖

### 5.1 只写直接依赖

```cpp
export struct redis_health_component {
    static constexpr bean_name name{"redis-health"};
    using beans = type_list<redis_health::Endpoint>;
    using dependencies = type_list<redis_component>;
};
```

应用只选 `redis_health_component`：

```cpp
using components = type_list<redis_health_component>;
```

框架会在编译期把 `redis_component` 也加入组件清单，因此应用不需要重复列出
`redis_component`，也不需要列出它的 bean。

### 5.2 解析规则

- 直接依赖递归展开为组件闭包
- 被依赖的组件排在依赖者之前
- 同一组件在多条依赖路径中只出现一次（菱形依赖去重）
- 应用重复列同一个组件是幂等的
- 组件依赖成环 → 编译错，并打印环路径
- 依赖项必须是组件，否则编译错

### 5.3 组件依赖与 bean 依赖

两句分开看：

| 关系 | 写法 | 谁负责 |
|---|---|---|
| 组件依赖 | `dependencies = type_list<...>` | 框架在编译期补齐组件清单 |
| bean 注入 | 构造器参数 `T&` | 现有 DI 解析、拓扑排序 |

组件依赖只保证“需要的组件在清单里”；真正的注入关系仍由 DI 校验。
例如 `Endpoint(redis::Client&)` 仍然按类型注入 `redis::Client`。

如果组件 bean 依赖应用提供的接口，不需要在 `dependencies` 中声明组件，
直接构造器注入即可；应用必须提供对应 bean，否则启动期/编译期报缺依赖。

### 5.4 依赖没写全

- 组件 bean 注入的 bean 不在最终清单 → DI 编译错
- 组件依赖指向非组件 → 编译错
- 组件依赖成环 → 编译错
- 声明了依赖但实际没用到 → 允许（例如健康检查注册、路由等副作用）

## 6. 合并、去重与冲突

最终 bean 清单：

1. 应用全局命名空间自动扫描到的 bean
2. 组件闭包中第一个组件的 `beans`
3. 第二个组件的 `beans`
4. ...

规则：

| 场景 | 行为 |
|---|---|
| 应用 bean 与组件 bean 同类型 | 去重，保留应用扫描到的那份 |
| 两个组件贡献同一类型 | 去重；本质是同一个 C++ 类型 |
| 同一组件 `beans` 内重复类型 | 编译错 |
| 同一契约的多个实现 | 两者都保留；注入时用 `Named` 或唯一默认实例选择 |
| 两个组件注册相同路径 | 先合并先注册；应用 bean 优先 |
| 两个配置 bean 同前缀 | 允许，但应避免重复绑定 |
| 合并后 bean 数超过上限 | 编译错 |

路由优先级：

1. 应用 bean
2. 组件闭包中靠前的组件
3. 组件闭包中靠后的组件

## 7. 条件与 Profile

Profile 是 **bean 级**条件：

```cpp
class [[=Config{"redis"}]][[=Profile{"redis"}]] RedisProps { ... };
class [[=Bean{}]][[=Profile{"redis"}]] RedisClient { ... };
```

未激活时：

- bean 不构造、不挂载
- 不读取该 bean 的配置
- 依赖它的 active bean 在启动期报错

组件的 `dependencies` 只保证编译期包含，不保证运行期激活。
如果依赖组件的 bean 全部因 Profile 未激活，而依赖者又需要它，启动期会报：

```text
cboot: bean 'A' requires 'B' which is inactive under profile (active: ...)
```

组件文档应写明所需的 Profile。

## 8. 编译期诊断

诊断统一以 `cboot:` 开头，尽量带组件名/bean 名。

| 场景 | 诊断示例 |
|---|---|
| `components` 类型不对 | `cboot: 'App::components' must be a type_list of components` |
| 根组件不是组件 | `cboot: 'X' is not a Component (missing beans/dependencies type list)` |
| 依赖项不是组件 | `cboot: component 'A' depends on 'X' which is not a Component` |
| 组件环 | `cboot: component dependency cycle: A -> B -> A` |
| 组件 bean 在全局命名空间 | `cboot: component bean 'X' must not be a direct member of the global namespace` |
| 组件 bean 缺身份注解 | `cboot: component 'A' bean 'X' lacks [[=Bean{}]] or [[=Config{...}]]` |
| 控制器漏标 Bean | `'X' has route methods but lacks [[=Bean{}]] annotation` |
| 同一组件 bean 重复 | `cboot: component 'A' lists bean 'X' more than once` |
| 组件数超限 | `cboot: component closure exceeded capacity` |
| 合并后 bean 超限 | `cboot: merged bean list exceeds capacity 128` |
| bean 依赖缺失 | `'Endpoint' requires 'redis::Client' which is not in the bean list` |

## 9. 组件编写规约

### 9.1 模块与可见性

- 模块名 `cboot.<组件名>`
- 描述符和 bean 类型都 `export`
- 依赖组件的描述符类型可见（import 或 export import）
- CMake target 以 PUBLIC 链接依赖组件

### 9.2 命名空间

- 组件 bean 全部放在组件自己的 namespace
- 不把组件 bean 放在全局命名空间
- 全局命名空间只放应用 bean

### 9.3 Bean 契约

- 普通 bean 标 `[[=Bean{}]]` 或 `[[=Bean{"name"}]]`
- 配置 bean 标 `[[=Config{"prefix"}]]`
- 控制器标 `[[=Bean{}]]`
- 构造器注入使用 `T&`；多构造器标 `[[=Inject{}]]`
- 同基类多实例用 `[[=Bean{"name"}]]` + `[[=Named{"name"}]]`
- 生命周期用 `[[=PostConstruct{}]]` / `[[=PreDestroy{}]]`
- 条件装配用 `[[=Profile{"name"}]]`
- 路由、事件、定时方法注解按现有规则

### 9.4 组件契约

- `using beans = type_list<...>;` 列全本组件 bean
- `using dependencies = type_list<...>;` 只列直接依赖组件
- `using hooks = type_list<...>;` 可选；hook 提供嵌套 `instance<Ctx>`
- 描述符本身不加 `[[=Bean{}]]`
- 同一 `beans` 列表不重复类型
- `name` 使用 `bean_name`

### 9.5 禁止项

- 运行期注册、服务定位器、静态初始化注册
- 组件依赖成环
- 组件 bean 直接读取全局配置
- 新增角色注解
- 依赖运行期动态加载

## 10. 构建与使用

### 10.1 组件包结构

```text
packages/redis/
├── CMakeLists.txt
├── redis.cppm              # 模块接口单元
├── src/redis.cpp           # 实现单元（可选）
├── test/redis_smoke.cpp    # 包内测试（可选）
└── README.md
```

模块名 `cboot.redis`；CMake target `cboot_redis`，别名/导出名 `cboot::redis`。

### 10.2 组件 CMake

```cmake
# packages/redis/CMakeLists.txt
cboot_component(redis
    VERSION 0.1.0
    MODULES redis.cppm
    SOURCES src/redis.cpp
    DEPENDS meta core config
    PACKAGE_DEPENDS cboot.<依赖组件>   # 可选
    TEST_SOURCES test/redis_smoke.cpp  # 可选
)
```

独立于 cboot 源码树构建时：

```cmake
find_package(cboot REQUIRED)
include("${cboot_CMAKE_DIR}/cbootComponent.cmake")
enable_testing()
```

`DEPENDS` 是模块/链接依赖；`PACKAGE_DEPENDS` 用于生成
`find_dependency(<组件包>)`，应用只选顶层组件时也能找到传递依赖。

### 10.3 应用 CMake

```cmake
find_package(cboot REQUIRED)
find_package(cboot.redis REQUIRED)

add_executable(app main.cpp)
target_link_libraries(app PRIVATE
    cboot::app
    cboot::redis)
```

`import cboot.app` / `import cboot.redis` 的模块 provider 必须**直接链接**；
不要依赖传递链接。

### 10.4 安装布局

```text
<prefix>/
├── lib/libcboot_redis.a
├── share/cboot/modules/redis/redis.cppm
├── share/cmake/cboot/cbootConfig.cmake
└── share/cmake/cboot.redis/cboot.redisConfig.cmake
```

组件包配置会先 `find_dependency(cboot)`，再导入自己的 target。

### 10.5 独立示例

`examples/standalone` 是 `find_package(cboot)` 消费示例，默认
`CBOOT_SDK_DIR=<repo>/build-release/install`：

```bash
cmake -S examples/standalone -B examples/standalone/build -G Ninja \
  -DCMAKE_BUILD_TYPE=Release
cmake --build examples/standalone/build
```

指定其他 SDK 前缀：

```bash
cmake -S examples/standalone -B examples/standalone/build -G Ninja \
  -DCBOOT_SDK_DIR=/path/to/cboot-install
```

## 11. 完整示例

### 11.1 缓存组件

```cpp
// cboot.cache.cppm
export module cboot.cache;

import std;
import cboot.core.annotations;
import cboot.meta.reflect;

export namespace cache {

struct [[=Bean{}]] MemoryCache {
    int get(int id) const { return id * 2; }
};

} // namespace cache

export struct cache_component {
    static constexpr bean_name name{"cache"};
    using beans = type_list<cache::MemoryCache>;
    using dependencies = type_list<>;
};
```

### 11.2 依赖缓存的健康检查组件

```cpp
// cboot.cache.health.cppm
export module cboot.cache.health;

import std;
import cboot.cache;
import cboot.core.annotations;
import cboot.meta.reflect;

export namespace cache_health {
struct [[=Bean{}]] Check {
    Check(cache::MemoryCache& cache) : cache_(cache) {}
    cache::MemoryCache& cache_;
};
}

export struct cache_health_component {
    static constexpr bean_name name{"cache-health"};
    using beans = type_list<cache_health::Check>;
    using dependencies = type_list<cache_component>;
};
```

### 11.3 应用

```cpp
import cboot.app;
import cboot.cache.health;

struct App : application<App> {
    using components = type_list<cache_health_component>;
};

int main() { return App{}.run(); }
```

应用只选 `cache_health_component`；`cache_component` 和 `cache::MemoryCache`
由框架自动补齐。

### 11.4 真实组件：cboot.schedule

`cboot.schedule` 是一个只贡献 hook、不贡献 bean 的组件：

```cpp
export struct schedule_component {
    static constexpr bean_name name{"schedule"};
    using beans = type_list<>;
    using dependencies = type_list<>;
    using hooks = type_list<schedule_hook>;
};
```

应用选择后，`schedule_hook` 在 context 构造完成后扫描 `[[=Scheduled{...}]]`
方法并启动调度线程。完整用法见 [定时任务](定时任务.md)。

## 12. 限制

- 不做运行期安装、卸载、热更新
- 不做跨编译器/跨 ABI 的二进制插件
- 不提供 `provides` / `needs` 接口契约或 SPI 选择
- 不提供可选依赖；`dependencies` 都是必需组件
- 不做组件级运行期激活；Profile 是 bean 级
- 不从 bean 构造器自动反推组件依赖；依赖必须显式声明
- 组件 bean 不能放在全局命名空间，否则会被应用自动扫描
