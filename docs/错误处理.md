# 全局错误处理

`cboot.web.error` 提供统一的错误出口，等价于 Servlet Filter /
Spring Security `ExceptionTranslationFilter`：

```text
CORS              order -1000
ErrorHandler      order  -900   ← 全局错误 middleware
AuthGuard         order   100
route middleware
handler
```

`ErrorHandler` 是一个普通全局 middleware：捕获下游异常、接管 router
标记的 404/405/校验失败，然后交给应用注册的 `ErrorMapper`；没有
mapper 时使用默认响应。

## 1. 错误结构

```cpp
namespace web {

struct error_field {
    std::string field;
    std::string message;
};

struct error_info {
    int status;
    std::string code;          // "auth.unauthorized" / "not_found" / ...
    std::string message;
    std::string method;
    std::string path;
    std::string route_pattern;
    std::string subject;       // 403 时的用户
    std::vector<error_field> fields;
    std::vector<std::pair<std::string, std::string>> headers;
    std::exception_ptr cause;
};

}
```

`headers` 用于 `Allow`、`WWW-Authenticate` 等协议头；框架会把这些头
合并到最终响应，mapper 不必重复设置。

## 2. 默认响应

| 来源 | 状态 | 默认 body |
|---|---|---|
| 路由未命中 | 404 | `404 not found` |
| 方法不匹配 | 405 | `405 method not allowed` + `Allow` |
| 认证失败 | 401 | `{"error":"unauthorized"}` + `WWW-Authenticate: Bearer` |
| 授权失败 | 403 | `{"error":"forbidden"}` |
| DTO 校验 | 400 | `{"errors":[{"field","message"}]}` |
| handler 异常 | 500 | `500 <what()>` |
| 业务抛 `web::error` | 自定义 | 按 `error_info` |
| 解析失败 / body 过大 | 400 / 413 | 默认文本 |
| handler 超时 | 504 | 默认文本 |

解析阶段的 400/413 与 504 发生在进入 middleware 之前或 SLA 判定处，
和 Servlet 容器解析错误一样不经过 `ErrorHandler`。

## 3. 自定义错误响应

应用提供一个 Bean，标注 `[[=web::ErrorMapper{.order=N}]]`：

```cpp
class [[=Bean{}]] [[=web::ErrorMapper{.order = 10}]] ApiErrors {
public:
    std::optional<Response> handle(const web::error_info& info,
                                   const web::request_context& ctx) {
        if (info.status != 401 && info.status != 403)
            return std::nullopt;       // 回退下一个 mapper / 默认响应

        json::object body;
        body.emplace_back("error", json::value(
            info.status == 401 ? "unauthorized" : "forbidden"));
        body.emplace_back("code", json::value(info.code));

        Response r = json_response(json::value(std::move(body)));
        r.status = info.status;
        return r;
    }
};
```

- 按 `order` 升序执行，返回 `nullopt` 继续
- mapper 抛异常会被忽略并继续，避免二次错误
- `Allow` / `WWW-Authenticate` 由框架合并，不要求 mapper 设置
- mapper 只在启动期注册，请求期只读

不写 mapper 时保持默认响应。

## 4. 主动抛出错误

handler 或自定义 middleware 可以抛结构化错误：

```cpp
web::error_info info;
info.status = 409;
info.code = "task.conflict";
info.message = "task already exists";
throw web::error(std::move(info));
```

`ErrorHandler` 捕获后统一交给 mapper。认证失败也是同一路径：
`AuthGuard` 发布 `authentication_failed` / `authorization_failed` 事件后
抛出 401/403，不在 guard 内拼响应。

## 5. 读取 middleware 写入的属性

```cpp
const auto& session = ctx.get<auth::session>();
```

`request_context::get<T>()` 在属性不存在时抛 `std::logic_error`，由
`ErrorHandler` 转 500（fail-loud）。用于“上游 middleware 已保证写入”的
约定，例如 AuthGuard → `auth::session`。业务 handler 不需要重复判断
未登录，认证失败不会进入 handler。

## 6. 边界

- `ErrorHandler` 只管错误响应，不做认证/授权判定
- 事件（`authentication_failed` 等）仍是旁路通知，不能改变响应
- 应用自己返回的业务 404/409 不会被改写；只有框架标记的 `error_info`
  才进入 mapper
- 解析错误、超时属于 connector/SLA 层，当前使用默认文本
- order < -900 的自定义 middleware 位于 `ErrorHandler` 外层；
  其异常由 router 兜底为默认 500，不经过应用 mapper
- `ErrorHandler` 会把 5xx 记为 `error`、4xx 记为 `debug`；
  只记录 method/path/status/code，不记录 body/token（见 [日志](日志.md)）
