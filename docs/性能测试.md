# 性能测试（Performance Testing）

1. **cboot-framework 的 HTTP 服务能跑多快？**（不同负载形态下的吞吐与并发能力）
2. **与 Java 相比处于什么水平？**（同机、同客户端、同负载的对比）
3. **瓶颈在哪、边界如何？**

> 配套工具：`test/bench/bench.cpp`（压测/微基准）、
> `test/bench/bench_java/BenchServer.java`（Java 对照服务）。

---

## 1. 测试环境

| 项 | 值 |
|---|---|
| CPU | 8 核（物理机，Windows 10 26200） |
| cboot-framework | GCC 16.2（niXman MinGW），**Release**（`-O3 -DNDEBUG`） |
| Java 对照 | JDK 8u201（JIT），单线程 selector NIO，零框架最小实现 |
| 网络 | 回环（loopback），服务端与客户端为两个独立进程 |

**测试口径**：Release 构建；服务与客户端分进程；每轮 16 万请求，3 轮取中位，失败数须为 0。

---

## 2. 被测对象

### 2.1 cboot-framework 服务端配置项

| 参数 | 含义 | 测试取值 |
|---|---|---|
| `server_io` | 网络后端：`threads` / `iocp` / `epoll` | `iocp` |
| `workers` | 服务端工作线程数 | `1` / `8` |
| `max_connections` | 背压阈值：超限回 503 | 不限（0） |
| `handler_timeout_ms` | handler 预算：超支回 504 | 关闭（0） |
| `send_timeout_ms` | 慢客户端写超时 | 30s（默认） |

### 2.2 路由（负载形态）

| 路由 | 响应 | 对应业界基准 |
|---|---|---|
| `GET /ping` | `pong`（4 字节文本） | TechEmpower **plaintext** |
| `GET /json` | 小对象 JSON（反射流式序列化） | TechEmpower **JSON serialization** |

### 2.3 Java 对照服务

`test/bench/bench_java/` 提供两档对照（均为单线程 `Selector`、无框架）：

| 实现 | 每请求工作 | 用途 |
|---|---|---|
| `BenchServer.java` | 预编码完整响应；只解析请求行 | Java **零点参照**：应用几乎不做事，给出传输/I-O 循环的吞吐参考上限 |
| `BenchServerFair.java` | 与 cboot-framework 相同：路由 + 每请求 JSON 构造 + 逐请求响应头 + keep-alive | **同级应用**对比：同语义、同等每请求工作 |

本机没有 Netty/Jackson 依赖，因此同级档用手写 NIO 实现（惯用分配方式）；
真实 Netty 可用池化缓冲减少响应头分配，但仍需真实序列化，预计介于
"同级"与"零点"之间，需另装依赖后复测。

## 3. 参数说明

本节说明每个参数**控制什么**、**为什么存在**、以及**能用它得出什么结论**。

### 3.1 客户端参数

| 参数 | 含义 | 控制什么 | 用途 / 可回答的问题 |
|---|---|---|---|
| `<threads>` | 并发 keep-alive 连接数 | 客户端同时保持的连接数量；顺序模式下即同时在途请求数 | 模拟不同并发用户数。可回答：吞吐随并发如何变化、在何处饱和 |
| `<per_thread>` | 每条连接的请求数 | 测试时长与样本量（总数 = threads × per_thread） | 提高统计稳定性；不改变吞吐结论 |
| `--pipeline N` | 流水线深度：一条连接上同时未完成的请求数 | 每次收发承载的请求数 | N=1 测往返延迟与每请求固定成本；N>1 测服务端批量处理能力（系统调用被摊薄）。可回答：吞吐是延迟受限还是处理能力受限 |
| `--serve PORT` | 仅启动服务端 | 进程边界 | 与 `--client` 组成两进程，排除同机 CPU 争抢对测量的干扰 |
| `--client PORT` | 仅启动客户端，请求指定端口 | 被测目标 | 同一负载可打 cboot-framework 或其它实现（如 Java），保证对比公平 |
| `--dispatch` | 不建立连接，直接调用路由派发 | 无网络噪声 | 测协议层纯 CPU 成本。可回答：瓶颈在应用代码还是内核/客户端 |
| `iocp` / `threads` | 被测服务端网络后端 | I/O 模型 | iocp：完成端口，支持万级连接；threads：阻塞 IO + 线程池，连接数受线程数限制 |

### 3.2 服务端参数

| 参数 | 含义 | 控制什么 | 用途 / 可回答的问题 |
|---|---|---|---|
| `server_io` | 网络后端 | 连接处理模型 | 对比不同 I/O 模型的吞吐与连接规模 |
| `workers` | 工作线程数 | 服务端并行处理能力 | 观察多核扩展性，与 CPU 核数匹配。可回答：增加并行度是否仍能提升吞吐（不能则瓶颈在别处） |
| `max_connections` | 连接上限 | 超限返回 503 | 验证背压行为；测容量时设为 0 |
| `handler_timeout_ms` | 单请求处理时限 | 超时返回 504（执行完成后判定） | 验证 SLA 行为；性能测试设为 0 以免干扰 |
| `send_timeout_ms` | 响应写超时 | 慢客户端连接回收 | 防止连接被不读数据的客户端长期占用 |

### 3.3 输出指标

输出示例：

```
pipe-plain #1:    1230097 req/s  (159744 reqs, 0 failures)
```

| 指标 | 含义 | 说明什么 |
|---|---|---|
| `req/s` | 每秒成功完成的请求数（成功数 ÷ 耗时） | 该配置下的吞吐能力 |
| `reqs` | 成功请求总数 | 样本量；因 pipeline 整除，略少于 threads × per_thread |
| `failures` | 失败请求数 | 测试有效性：**必须为 0**，否则结果不可用 |
| `reconnects` | 客户端重连次数 | 服务端每连接 1024 请求上限导致的连接轮换，不代表错误 |
| `ns/req` | 微基准单次操作的平均 CPU 时间 | 应用层处理成本，用于定位瓶颈 |

### 3.4 按问题选参数

| 要回答的问题 | 参数组合 | 结论的含义 |
|---|---|---|
| 单请求延迟与每请求固定成本 | `8 20000 --client PORT`（depth=1） | RPS 受往返延迟限制；反映每请求固定开销 |
| 服务端吞吐上限 | `8 20000 --client PORT --pipeline 64` | 批量摊薄系统调用后的处理能力 |
| 连接容量 | `8 2000 iocp 10000` | 可同时维持并正确服务的连接数 |
| 应用层 CPU 成本 | `0 0 --dispatch` | 解析 + 路由 + 序列化的纯 CPU 时间 |
| 与其它实现对比 | 相同参数分别打两边 | 消除客户端差异后的服务端差异 |

### 3.5 结果解读规则

1. **只在相同参数下比较**：depth=1 与 depth=64 测的不是同一件事。
2. **判断瓶颈归属**：增加 `workers` 后吞吐不变 → 瓶颈在客户端或内核；吞吐上升 →
   此前受服务端并行度限制。
3. **考虑测量噪声**：同机客户端与服务共享 CPU，单轮波动可达 ±30%，以 3 轮中位数为准。

**示例**：`cboot_bench 8 20000 iocp --workers 8 --pipeline 64`
共 16 万请求；每连接约 312 批、每批 64 个在途请求；服务端 8 个 worker 共取完成端口
（单次最多 32 个完成包）。

## 4. 测试场景与方法

| 场景 | 形态 | 测什么 |
|---|---|---|
| **A 顺序**（depth=1） | 每连接发一请求→等响应→发下一个 | 单请求往返延迟决定的上限；每请求服务端成本 |
| **B 流水线**（depth=64） | 一次写 64 请求，再读 64 响应 | 批量摊薄系统调用后的纯处理吞吐 |
| **C 连接规模** | 10000 条 keep-alive 连接各发一请求 | 万级连接下的正确性与资源占用 |
| **D 每请求建连** | 每请求新建 TCP 连接 | TCP 握手成本（负面对照） |
| **E 派发微基准** | 直接调用 `router.dispatch` 200 万次 | 协议层每请求 CPU 成本（无网络噪声） |

## 5. 结果

### 5.1 cboot-framework（Release，8 连接，16 万请求，0 失败）

| 场景 | 配置 | plaintext | JSON |
|---|---|---|---|
| A 顺序 | IOCP `workers=1` | 45.7k req/s | 44.5k req/s |
| A 顺序 | IOCP `workers=8` | 71.9k req/s | 81.6k req/s |
| B 流水 depth=64 | IOCP `workers=1` | **1.25M req/s** | **0.94M req/s** |
| B 流水 depth=64 | IOCP `workers=8` | **2.11M req/s** | **2.07M req/s** |
| C 连接规模 | IOCP `workers=8` | 10000/10000 连接全部服务 | — |
| D 每请求建连 | IOCP | ~4–9k req/s | — |
| E 微基准 | 派发 / 会话（64/批） | **112 / 316 ns/req** | 224 / ~470 ns/req |

### 5.2 与 Java 对比（同机、同客户端、分进程、Release）

同场三档，同一客户端、轮转顺序；流水线 6 轮、顺序 5 轮取中位：

| 场景 | cboot-framework | Java 同级应用 | Java 零点（参照） |
|---|---|---|---|
| A 顺序 plaintext/JSON | ≈43–70k（轮间波动，无显著差异） | 同左 | 同左 |
| B 流水 plaintext | **0.94M** | 0.83M（-13%） | 1.16M |
| B 流水 JSON | **0.84M** | 0.72M（-17%） | 1.25M |
| C 连接规模 | 10000/10000 | 未测 | 未测 |
| D 每请求建连 | 4–9k | 未测 | 未测 |
| E 微基准 | 112 / 316 ns | — | — |
| B 多 worker | 2.11M（8 worker） | 单线程，不可比 | 单线程，不可比 |

**排序**：同等工作量（路由 + 每请求 JSON + 响应头）下
**cboot-framework > Java 同级应用**（+13% / +17%）。Java 零点不参与排序：它预编码
完整响应、不做路由/序列化/响应头，1.16M / 1.25M 只是传输层参考上限。

- **A 顺序**：depth=1 由 RTT 决定（8 连接 ÷ 56k ≈ 143µs），服务端每请求
  <1µs、占比 <0.5%。同场 5 轮中位：plaintext 56.7k / 55.7k / 58.8k，
  JSON 55.9k / 57.1k / 56.6k（cboot-framework / 同级 / 零点）；重复测试中排序会
  翻转（另一次 JSON 为 56.6k vs 55.5k），差异 ±2–7% 小于轮间波动，
  故该行**不排序**。
- **B 流水（零点参照）**：与同级应用的差值（-28% / -42%）对应 Java 每请求
  应用工作的成本；cboot-framework 与它的差值（-19% / -33%）含应用工作与框架开销。
- **C/D/E**：仅 cboot-framework 侧测量；Java 对照没有连接规模/建连/微基准模式。
- **多 worker**：cboot-framework 用 8 核，Java 对照单线程，非核心对等。
- **时段说明**：安静时段（§5.1）cboot-framework 基线为 A 45.7k/44.5k、B 1.25M/0.94M，
  当时零点实现为 A 44.1k/42.9k、B 1.27M/1.10M；本节为同场三档（负载偏高），
  绝对值不跨时段相减，排序只看同场数据。

## 6. 结果解读

- **场景 A（顺序）**：吞吐由 RTT 决定（≈ 连接数 ÷ RTT）；同一实现在不同轮次
  可相差 ±30%，cboot-framework 与 Java 各次互有高低（±2–7%），属测量噪声，
  不按该行排序。
- **场景 B（流水线）**：吞吐由每请求 CPU 成本决定（批量摊薄了系统调用）。
  plaintext：cboot-framework ≈ 0.80µs/请求 vs Java ≈ 0.79µs/请求 → **同一水平**；
  JSON 项因工作量不对等（真实序列化 vs 硬编码字节）不作效率结论。
- **同级应用（§5.2）**：同样做路由、序列化与响应头时，cboot-framework 每核高
  **13%（plaintext）/ 17%（JSON）**；零点实现的更高吞吐对应少做应用工作，
  不是语言优势。
- **场景 C**：IOCP 后端可承载万级连接；`threads` 后端在同参数下受 worker
  排队限制（连接数不是线程数的函数）。
- **场景 E**：详见下方"每请求成本分解"；用于把服务端成本从网络噪声中分离。

### 6.1 每请求成本分解（Release 微基准，无网络）

| 环节 | plaintext | JSON |
|---|---|---|
| 路由派发（含 handler + Response 构造） | 112 ns | 224 ns |
| 其中：`Response::text` / `json_response` | 24 ns | **127 ns** |
| 响应序列化（头部 + 追加） | 43 ns | 43 ns |
| **完整会话**（解析 + 派发 + 序列化，64/批） | **316 ns/req** | ~470 ns/req |
| 流水线实测总时间（1 worker） | ≈ 800 ns/req | ≈ 1060 ns/req |

**关于 JSON 的 127ns**：反射遍历/流式写入本身只占小部分；其余是整数格式化、
字符转义与响应体拷贝。此前的主要成本是**响应体第一次超过 `std::string`
短字符串上限（15 字节）触发的一次堆分配**；改为 64 字节内联缓冲后该项消失
（187ns → ~127ns）。
（Java 零点对照返回预编码字节，不做序列化；同级应用对照逐请求构造 JSON，
见 5.2。）

**关于总体差距为什么不大**：单请求总时间 ≈ 800ns，其中服务端应用代码只占
≈ 316ns（约 40%），其余是**内核收发 + 客户端解析 + 回环调度**。应用层快 2 倍，
总时间也只能改善约 15–20%——该负载是**系统调用/内核受限**，不是 CPU 受限。
C++ 的优势要在大响应体、真实业务计算、无 GC 停顿等 CPU 密集场景才充分体现。

**结论**：与**同级应用**相比，cboot-framework 每核高 13–17%，差距来自零分配热路径；
与**零点实现**相比低 19–33%，差值就是每请求序列化与响应头构造的成本。
两种对比都表明：该负载下约 60% 时间在内核/传输，应用层优化只能改变十位数
百分比；多 worker 总量 2.1M+，万级连接能力已验证。

## 7. 局限

- **Java 对照是 JDK 8 / Windows**：Windows 下 JDK Selector 基于 `select()`
  （O(n)、fd 上限 1024）；Linux 下 JDK 用 epoll 会更快。本机数字对 Java 偏保守，
  跨平台结论需 Linux + JDK 21 + Netty 复测。
- **同级应用也是手写 NIO**：本机无 Netty/Jackson 依赖，同级档按惯用写法
  逐请求分配 String/byte[]；Netty 池化缓冲可减少响应头分配，但仍做真实
  序列化，需另装依赖复测。
- **JDK 21 Loom 不影响本结论**：plaintext 负载是 I/O + 解析；虚拟线程改善的是
  阻塞型业务，Windows 下 NIO 仍走 select。
- **多 worker vs 单线程非核心对等**：cboot-framework `workers=8` 用 8 核，Java 对照 1 线程；
  若 Java 用 8 线程（Tomcat）也会扩展。
- **客户端可能成为上限**：同一 C++ 客户端逐响应解析，两种服务都趋近其处理上限。
- **压测客户端必须用 RST 关闭**：每连接 960 请求后主动重连，若优雅关闭，
  数十轮后 16,384 个临时端口会被 `TIME_WAIT` 耗尽，表现为所有服务同时
  "拒绝连接"（与语言/框架无关）。`bench_close` 用 `SO_LINGER=0` 规避。
- **生产特性开销**：cboot-framework 侧含 keep-alive 超时、单连接请求上限、背压、
  handler SLA 等检查，Java 基准服务没有。
- **回环网络**：无真实网卡/RTT 影响；跨机压测需另做。

## 8. 复现

```bash
# cboot-framework（Release）
./build-release/test/cboot_bench 0 0 iocp 0 --workers 1 --serve 18100 &
./build-release/test/cboot_bench 8 20000 --client 18100                # 顺序
./build-release/test/cboot_bench 8 20000 --client 18100 --pipeline 64  # 流水线
./build-release/test/cboot_bench 8 2000 iocp 10000                     # 连接规模
./build-release/test/cboot_bench 0 0 --dispatch                        # 派发微基准

# Java 对照（零点：预编码响应）
javac -encoding UTF-8 test/bench/bench_java/BenchServer.java
java -cp test/bench/bench_java BenchServer 18104 &
./build-release/test/cboot_bench 8 20000 --client 18104 --pipeline 64

# Java 同级应用（逐请求 JSON 构造 + 响应头）
javac -encoding UTF-8 -d test/bench/bench_java test/bench/bench_java/BenchServerFair.java
java -cp test/bench/bench_java BenchServerFair 18105 &
./build-release/test/cboot_bench 8 20000 --client 18105 --pipeline 64
```
